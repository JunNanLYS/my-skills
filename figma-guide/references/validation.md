# validation.md

本文件只讲收尾验证与父框改动后的安全流程。

## 1. 验证三步法

每个任务完成后，至少做三层验证：

1. **结构层**：确认关键节点存在、位置正确、层级未漂移。
2. **视觉层**：导出目标节点，生成 PNG。
3. **业务层**：打开截图逐项检查，确认没有肉眼可见问题。

导出成功不等于视觉正确。真正交付以前，必须看图。

## 2. 截图必 Read

导出结果常见的“成功但仍然错误”包括：

- 文字被裁切。
- 颜色落到错误值。
- 元素被遮挡或覆盖。
- 实例 override 没生效。
- 间距或对齐出现 1–2px 漂移。

因此必须遵守：

- 导出后先写盘。
- 打开 PNG 逐项确认。
- 没有看过图，就不能向用户报告“已完成”。

## 3. 截图核对清单

看图时重点检查：

- [ ] 文字是否完整，无截断、无超框。
- [ ] 颜色是否与设计要求一致。
- [ ] 是否有遮挡、重叠、层级错误。
- [ ] 卡片、列表、按钮之间的间距是否均匀。
- [ ] 圆角、描边、阴影是否符合项目 token。
- [ ] 父框与子节点是否对齐。
- [ ] 实例状态和 override 是否真的生效。

## 4. 截图保存原则

推荐目录：

```text
<项目根>/temp/figma/
```

建议流程：

1. 首次保存前确保目录存在。
2. 导出结果先落盘为 PNG。
3. 若重复导出同一张图，避免误读旧文件。
4. 命名带页面或功能语义，便于回看。

## 5. 导出方式的当前主路径

导出与截图验证默认优先使用 `figma-cli` 原生命令：

- `figma-cli verify --save`
- `figma-cli export screenshot -o ...`
- `figma-cli export node <nodeId> -o ...`

原则：

- 优先让 CLI 直接把 PNG 写到磁盘。
- 不再回退到“先拿 base64，再靠本地脚本转存 PNG”的旧工作流。
- 导出写盘后必须实际打开图看，而不是只看命令返回成功。

## 6. 改父框尺寸时的推荐流程

只要改复合结构父框 `w / h`，默认按下面顺序思考：

### Step 1：优先使用 CLI 原生命令调整布局

优先考虑这些方向：

- `figma-cli set autolayout ...`
- `figma-cli pin ...`
- `figma-cli sizing ...`
- `figma-cli inspect ...`
- 其他当前 `figma-cli --help` 能确认的布局/约束命令

也就是说：

- 不要默认把父框改动理解成“必须先跑一个本地重算脚本”。
- 先看当前节点本来是不是就该通过 auto-layout、pin、sizing 等方式表达。

### Step 2：怀疑越界时，再做离线几何审计

如果父框尺寸变化后，你怀疑出现了这些问题：

- 左/上溢出。
- 右/下溢出。
- 被裁切但不确定是不是原本就存在。
- 局部坐标或层级变化导致的隐藏布局问题。

这时再运行 `figma-validate-bounds.mjs` 拿基线或做复查。

这一步的目的不是代替布局，而是：

- 把“改之前”的问题和“改之后”的问题区分开。
- 给复杂结构提供一份机器可读的几何审计结果。

### Step 3：改完后再审一次

如果这次任务涉及复杂父子结构、reparent、批量位移或裁切风险，改完之后再跑一次 `figma-validate-bounds.mjs`。

只有当：

- 几何审计没有新增问题，且
- PNG 截图核对也通过，

这轮父框改动才算真正通过。

## 7. 完工前自检

- [ ] 重复结构已优先复用，没有重复重画。
- [ ] 组件定义留在组件页，UI 页只消费复用结果。
- [ ] 关键节点已重新读取验证，没有继续使用旧 NodeId。
- [ ] 颜色 / 字号 / 圆角 / 间距遵循项目设计系统。
- [ ] 新 Section 已复刻现有模式，而不是凭印象设尺寸。
- [ ] 父框改动优先使用 CLI 原生命令，而不是先假设需要本地重算脚本。
- [ ] 若存在复杂父子结构风险，已做过一次或两次 bounds 审计。
- [ ] 导出图已经写盘，并实际打开检查过。
- [ ] 用户看到的结论基于截图核对，不是基于“导出成功”。
